# Private operation and recovery

Use the root README for a fresh installation. Compose runs PostgreSQL 17.9 with a named volume, an explicit one-shot migration service, and a non-root Node application process behind Docker's init process. The database and dashboard bind only to loopback on the host. No public cloud or paid service is provisioned.

## Configuration

`pnpm run init` generates random database, session and setup secrets in `.env` and copies it to `apps/tally/.env.local`. Node 24 and pnpm 11.19.0 are required. For Compose the database URL is overridden to the internal `db` host; for local Node development it uses loopback port 55487. Never put the authentication secret or setup token in `NEXT_PUBLIC_*`, source control, images, logs or client configuration. The public ingestion UUID is safe to embed and is write-only.

First-owner setup requires the server token and uses a transaction with a singleton installation row, preventing concurrent ownership creation. After setup the token cannot create another owner. Remove `SETUP_TOKEN` from server configuration after successful setup if desired, then restart the app. Owner recovery does not require that token.

For private remote access, use a trusted HTTPS reverse proxy or VPN with an HTTPS origin. Set `BETTER_AUTH_URL` to that exact HTTPS origin, restart, and use the same host in your browser. Better Auth will emit Secure cookies on HTTPS; HttpOnly and SameSite protect session tokens. Do not directly expose PostgreSQL. Configure proxy body limit 64 KiB for ingestion and a finite client request timeout (for example 15 seconds), reject malformed framing, and restrict network access appropriately. Do not cache `/api/*`. No production TLS certificate is generated by Tally.

Sessions expire after eight hours, with library-managed renewal on use. Logout revokes the session. Owner-only report/settings/export endpoints resolve the session and project ownership server-side. Mutation requests require the configured Origin. A public ingestion UUID does not substitute for a session. The global five-attempt/minute login budget deliberately avoids trusting spoofable forwarded IP headers in a one-owner installation.

## Start, stop and health

```sh
docker compose --profile app up --build -d
docker compose ps
docker compose logs --tail 50 app
docker compose --profile app stop
```

Stopping preserves the named volume. Do **not** use `down -v` unless you intend to delete all active data. Docker uses an init process, forwards termination signals and allows 30 seconds for graceful shutdown. In-flight writes may still have ambiguous transport status during a shutdown; SDK UUID retries are idempotent. PostgreSQL commits and durable volume storage are the source of truth.

`GET /api/health` is liveness. `GET /api/ready` checks database schema access and is uncached. Both responses avoid sensitive details. Migration service failure prevents the application service starting; investigate before retrying. Resource limits: database 768 MiB; application 1.5 GiB. Docker builds need additional temporary memory/disk. The development server is for loopback use only; use production builds for real data.

## Retention

Default 30 days. Run at least daily:

```sh
docker compose --profile app run --rm app pnpm retention
```

Or, with local Node/database connectivity:

```sh
pnpm retention
```

Schedule that command using your system scheduler (cron or Windows Task Scheduler), with the repository as working directory and protected environment access. Tally does not create a background alert or scheduler. Record only numeric deletion counts and success/failure, not event contents. Cleanup removes entire expired workflow/ invocation groups by earliest observed start (or earliest event when a start is missing), including later events, then clears expired limits, sessions and verifications. No materialized analytics table exists to reconcile. Reports can change after cleanup.

## Back up and restore

Protect backups as sensitive administrative data: they include the hashed owner password and active session records as well as telemetry. Encrypt them at rest using your storage tooling and restrict access. A reasonable initial policy is daily backups, seven daily copies, four weekly copies, then deletion. This is an operator policy, not an automated promise by Tally. Deleting a project from active storage does not erase existing backups.

Create a binary PostgreSQL custom-format dump without PowerShell text redirection:

```sh
pnpm exec tsx scripts/backup.ts backup backups/2026-09-08.dump
```

Create the `backups` directory first. The script refuses to overwrite a file and streams binary output directly. It uses the Compose `db` container's database access; secrets are not placed in shell arguments. In a container-only workflow the equivalent is:

```sh
docker compose exec db pg_dump -U tally -d tally -Fc -f /tmp/tally.dump
docker compose cp db:/tmp/tally.dump backups/tally.dump
```

Restore into a **new separate database**, never over the running one:

```sh
pnpm exec tsx scripts/backup.ts restore backups/2026-09-08.dump tally_restore_verify
```

The restore script only permits names prefixed `tally_restore_` and refuses existing databases. Compare project/event counts and inspect representative reports, then test readiness with a separate application process pointed at the restored database. To recover service, stop the app, change `DATABASE_URL` to the verified restored database in the app's runtime configuration (including the Compose environment override), start it, and verify authentication/reports. A backup may restore previously deleted records and old sessions: revoke sessions through owner recovery before exposing the restored app. Preserve the original database until recovery is verified.

`pnpm test:operations` exercises restart persistence, binary restore into `tally_restore_check`, an additive migration in `tally_upgrade_check` with existing representative records, and whole-invocation retention. It is a test-only command, not a production maintenance command.

## Owner recovery (requires server access)

Set process environment variables without putting the password in command-line history. In PowerShell:

```powershell
$env:TALLY_OWNER_EMAIL = Read-Host 'Owner email'
$taskSecurePassword = Read-Host 'New owner password (12–128 characters)' -AsSecureString
$env:TALLY_OWNER_PASSWORD = [System.Net.NetworkCredential]::new('', $taskSecurePassword).Password
pnpm owner:recover
Remove-Item Env:TALLY_OWNER_PASSWORD
Remove-Item Env:TALLY_OWNER_EMAIL
```

For container operation, pass the already populated environment by name:

```sh
docker compose --profile app run --rm -e TALLY_OWNER_EMAIL -e TALLY_OWNER_PASSWORD app pnpm owner:recover
```

The recovery command delegates hashing to Better Auth, changes the existing owner's login, and revokes **all** sessions. It does not create a second owner or discard projects. Clear the temporary environment afterward. If `.env` was lost, restore it from protected server configuration; changing `BETTER_AUTH_SECRET` also invalidates signed sessions and requires restarting every instance.

## Upgrade and rollback

1. Read the changelog and schema compatibility notes for the target version. Record current source revision/image and configuration.
2. Back up and restore-test the current database. Quiesce the collector or stop the application during migration.
3. Obtain the target source, run `pnpm install --frozen-lockfile`, then build the target container.
4. Run the explicit migration service: `docker compose --profile app run --rm migrate`.
5. Start the application: `docker compose --profile app up -d app`. Verify readiness, login, project access and known report samples.
6. Update SDK archives in applications independently. SDK 0.1.0 remains schema 1; unsupported event schemas receive permanent 400 responses.

The initial-to-second migration adds only an index and was tested with existing records. It does not require application code changes and the previous schema-compatible application can read the upgraded database. **No destructive down-migration or general migration rollback is verified.** If a future migration is incompatible, recover a verified backup into a new database and run the matching application revision; later accepted events are absent from that backup. Do not blindly run `migrate reset` or modify an applied migration.

## Performance and limits

See `PERFORMANCE.json` for the measured environment and workload. It records ingestion latency/throughput and report response latency for 5,000 events, 100 requests in batches of 50, concurrency 5, and ten report requests. It is a bounded local test, not a scalability claim. Reports currently load up to 50,000 retained events per project and refuse larger working sets; use small private workloads, appropriate retention and quotas. Increasing write quotas does not increase report capacity.
