# Tally v1 contract

Tally 1.0 supports small private installations with one owner, up to 20 projects, and reports over at most 50,000 retained events per project. The supported self-hosted path is Node 24, pnpm 11.19.0, PostgreSQL 17.9 and the repository's Docker Compose configuration. The separately maintained hosted service has its own integration guide and verification history.

## Install and build

Use the tagged source archive generated by GitHub for a published release. Follow the root README to generate private secrets, build the application image locally from that tagged source, start the database and application, create the owner, create a project, and connect the SDK. No paid service or model credential is required. No application image registry is promised.

The release's SDK archive includes ESM, CommonJS, TypeScript declarations, its README and MIT license. It has no runtime dependencies or imports from the monorepo. Install the local tarball in your own application; `@tally-local/sdk` is a provisional archive name, not a claimed or published npm namespace. The SDK supports Node 20 or newer and modern browsers with `fetch`; the application requires Node 24.

The root README's Verify section gives the developer workflow. Run its integration and operations tests only against a disposable installation. The independent consumer test uses a fresh directory outside the workspace, installs the packed SDK, compiles a separate TypeScript consumer and sends actual collector requests.

## Compatibility

Within v1, the documented SDK exports and schema 1 ingestion fields remain supported. Breaking changes to those contracts require a major version. SDK versions and event schema versions are independent; SDK 1.0 sends schema 1. Unsupported schemas are explicitly rejected rather than silently converted.

The SDK preserves synchronous callback values and native Promise fulfillment/rejection values, executes a callback once, and collects allowlisted metadata. Promise object identity and custom thenables are outside the contract. Delivery remains bounded and best effort: queue overflow, unload and failed requests can lose events. Source labels describe the application's observation, not verified caller identity or business truth.

The WebMCP browser API is a changing draft. The application feature-detects it and keeps ordinary controls usable without native support. Native compatibility claims apply only to the browser and flags recorded in an executed check, not to all browser agents. No unwrapped callback or automatic provider attribution is measured.

Database migrations are explicit. No schema change is introduced by the 1.0 version labels. Remote HTTPS, host access, secret protection, backups, retention scheduling and workload capacity remain operator responsibilities. See the operations and privacy documentation for the full limits.

## Upgrade from 0.1

1. Stop application writes and make a database backup using the operations guide. Keep the private `.env` and backup outside any source directory that you replace.
2. Extract the new tagged source into a new directory. Copy the same private `.env` there. Preserve the Compose project name so the existing database volume is selected; the checked-in name is `tally-private`.
3. Follow the operations upgrade procedure to build the application, run the explicit migration service and restart it. Check owner sign-in, existing projects and a known report before accepting new writes. Version 1.0 adds no new migration.
4. Replace local SDK tarballs in instrumented applications separately, then check a known callback and its dashboard receipt. Existing schema 1 clients remain compatible.

Avoid running `pnpm init` over existing settings or using `docker compose down --volumes` as an upgrade command. Returning to a previous source version requires evaluating migrations and restoring a reviewed backup when needed; a version label alone does not undo a database change.

## Release gate

A release is published only from an exact main commit whose full verification job passed. The job checks production builds, unit tests, production dependency audit, owner setup and browser flow, strict ingestion, independent SDK use, native execution, backup/restore, upgrade, recovery and capacity fixtures. It then uploads the tested SDK archive and its SHA256 checksum. Publication uses a draft until every expected asset and tag commit is verified.

The release gate establishes this bounded supported workflow. It does not promise zero defects, arbitrary installation scale, legal clearance for redistributing all dependencies, or compatibility with every browser. Maintenance follows the initial release.
